Data Representations

A production-and-research treatment organized for engineers who already understand ML, neural networks, and Transformer fundamentals. Each chapter is deliberately split into two reading pages: mechanism first, then systems, failure modes, and research reasoning.

In plain English

Every dataset, feature store, and training corpus is ultimately bytes on disk in some chosen format, some chosen data model, and some chosen serialization — and that choice quietly decides how fast you can read it, how safely you can change it, and how many other systems can share it.

PAGE 1 · MECHANISM, MENTAL MODEL, THEORY

1. Quick explanation

Data representation is the combined choice of file format (CSV, JSON, Parquet, Avro, ORC), data model (relational, document, graph, columnar), and encoding/serialization scheme (text vs binary, schema-on-write vs schema-on-read) that determines how information is stored, queried, evolved, and moved between systems.

2. What problem does this solve?

Problem. Raw values (numbers, strings, nested records, timestamps) have no inherent byte layout; every system that reads or writes them must agree on a shared, unambiguous encoding, and that encoding has to remain compatible as schemas evolve and as different workloads (row-at-a-time transactional access vs column-scan analytical access) pull it in opposite directions.

Problem → constraint → design: Data has no self-describing byte layout → competing access patterns (row lookups vs column scans) and schema evolution across producers/consumers → choose a data model, a physical layout (row-oriented vs column-oriented), and a serialization format with an explicit schema evolution contract.

Why engineers care: removing the ambiguity of "just write it as text" transfers pressure to schema compatibility and read/write amplification. A format that is easy to write by hand (CSV, ad hoc JSON) is usually expensive to validate, evolve, and scan at analytical scale; a format optimized for analytical scans (Parquet, ORC) is usually a poor fit for high-frequency row updates.

3. How to think about it

        │
        ▼

        │

        ▼
Bytes on disk / on the wire, readable by every downstream consumer

A useful way to think about it: a data format is a contract between writers and readers that trades human-readability and flexibility (text formats, schema-on-read) for machine-efficiency and safety (binary formats, schema-on-write, strong typing).

Where this analogy stops helping: the "best" format is not universal — a relational/row store excels at point lookups and transactional updates, while a columnar store excels at scanning a few columns across billions of rows; picking one for the wrong workload does not just cost performance, it can make certain queries structurally impossible to run efficiently.

4. What is happening under the hood

  1. Represent the state. A logical record (an event, a row, a document, a graph node/edge) is mapped onto a data model: relational tables with fixed columns, JSON/BSON documents with nested and variable structure, property graphs with nodes/edges/properties, or wide-column/columnar stores keyed by column family.
  2. Execute the topic-specific transformation. The record is serialized: text formats (CSV, JSON) encode values as human-readable strings with a delimiter or bracket grammar; binary formats (Avro, Protobuf, Thrift) encode values against a schema using compact binary tags and lengths; columnar formats (Parquet, ORC) additionally reorganize storage so that each column's values are stored contiguously, enabling per-column compression (dictionary encoding, run-length encoding) and predicate pushdown.
  3. Apply constraints and allocate resources. The schema (explicit, as in Avro/Protobuf/relational DDL, or implicit, as in CSV/JSON) constrains which types are legal, and the storage layout constrains which access patterns are cheap: row stores are cheap for "read/write one whole record"; column stores are cheap for "read one attribute across many records" and expensive for "read/write one whole record."
  4. Preserve the right state. Schema evolution rules (Avro's writer/reader schema resolution, Protobuf's numbered/optional fields, Parquet's schema merging) let old data remain readable as the schema adds, removes, or renames fields — this is what Kleppmann calls maintaining forward and backward compatibility across rolling deploys.
  5. Validate the failure boundary. The primary failure pressure is schema drift silently corrupting downstream consumers — a writer adds a field, changes a type, or reorders columns, and readers that assumed positional or implicit typing either crash or silently misinterpret data.
Schema-on-write (validate before storage; relational, Avro, Protobuf) vs schema-on-read (validate at query time; JSON, log files, data lake raw zone) — the trade-off is write-time safety vs read-time flexibility.

The resource that usually becomes the problem: I/O amplification from choosing the wrong row/column orientation for the dominant query pattern, and schema-compatibility breakage across independently-deployed producers and consumers.

6. How it scales

At a high level, as the workload grows: the number of columns read per query, the number of independent producers/consumers of a schema, and the total data volume all grow independently, and each stresses a different part of the format choice. The practical bottleneck is I/O amplification and schema-compatibility breakage, which may dominate before raw storage cost does.

T_request = T_queue + T_compute + T_memory + T_network + T_validation

The practical question is: at what column count, query selectivity, and producer/consumer count does reading unnecessary bytes (wrong row/column orientation) or a breaking schema change become the first saturated resource? That threshold is more actionable than a single "use Parquet" rule.

7. How it works in production

    ↓

    ↓

    ↓

    ↓
Ack + downstream propagation

A practical production starting point: use a schema registry (Confluent Schema Registry for Avro/Protobuf on Kafka) to enforce compatibility rules at write time; store operational/transactional data row-oriented (Postgres, MySQL); land analytical/lake data columnar (Parquet with Snappy/Zstd compression, queried by Spark, DuckDB, or Trino); never let a JSON blob become the source of truth without a validated schema (JSON Schema, or a typed wrapper) once more than one team consumes it.

  • Keep durable state behind explicit ownership boundaries.
  • Make workers independently replaceable.
  • Version caches and artifacts.
  • Isolate slow or failure-prone dependencies behind queues, deadlines, and budgets.

Use the simpler approach when: the data is exploratory, single-team, or short-lived (a one-off notebook export). Use the more production-ready approach when: more than one service or team reads the same schema and needs a compatibility contract. Choose advanced optimization when: analytical scan cost or compression ratio is a measured, material cost driver. Avoid both naive simplification and premature optimization when: you haven't yet measured whether the workload is point-access or scan-heavy.

10. Common misunderstandings

Misconception: "JSON is schema-less, so it's more flexible and therefore safer."
Reality: JSON has no schema enforcement, which means every consumer independently guesses the schema, and drift is discovered at read time by whichever consumer breaks first, not at write time.
Why people believe it: schema-on-read feels agile during early development, when there is only one consumer.

Misconception: "Parquet/columnar formats are strictly 'better' than row formats."
Reality: columnar formats are better for wide analytical scans over few columns; they are worse for high-frequency single-record reads/writes because a small update forces rewriting compressed column chunks.
Why people believe it: most public benchmarking is analytics-oriented, so it advertises the columnar win without stating the transactional workload it is not designed for.

Misconception: "The data model (relational vs document vs graph) is a stylistic preference."
Reality: the data model encodes which relationships are cheap to traverse — foreign-key joins in relational, embedded documents in document stores, multi-hop traversal in graph stores — and picking the wrong one forces expensive application-level joins or denormalization.
Why people believe it: early-stage data volumes are small enough that any model "works," hiding the traversal cost until scale exposes it.

11. The point where this starts to hurt

The system appears scalable because a query returns correct results today, but the real bottleneck is schema-compatibility breakage and I/O amplification from the wrong row/column orientation. Capacity planning must therefore model the number of independent schema producers/consumers and the column-selectivity of the dominant query pattern — not only current storage size.

12. How to explain it in an interview (30–45 seconds)

"Data representation is the combined choice of data model, physical layout, and serialization format that determines how information is stored, queried, and evolved. It exists because raw values have no inherent byte layout, and different workloads — transactional point-lookups vs analytical column scans — want opposite physical layouts. Operationally, the core decision is schema-on-write with a registry (Avro/Protobuf) for anything more than one team consumes, row-oriented storage for transactional access, and columnar (Parquet/ORC) for analytical access. I think of it as choosing which access pattern gets to be cheap, because you cannot make every access pattern cheap simultaneously. The main trade-off is write-time safety and scan efficiency versus flexibility and point-update speed. In production I would measure both schema-compatibility violations and bytes-scanned-per-query, because a format that looks efficient in a demo can still amplify I/O or break consumers silently at scale."

13. Follow-up questions you may get

  1. What is the dominant resource at scale? Short answer: measure bytes scanned per query against bytes actually used, and count independent schema consumers to size compatibility risk.
  2. What assumption makes the mechanism work? The schema evolution rule (e.g. Avro's writer/reader schema resolution, Protobuf field numbering) assumes producers and consumers deploy independently and must never rely on positional field order.
  3. Where does it fail first? An uncoordinated schema change on a shared topic/table breaks the first consumer that assumed the old shape, often silently (wrong type coercion) rather than loudly (crash).
  4. What is the simplest production baseline? An explicit schema with a registry enforcing backward compatibility, row-oriented for OLTP, columnar for the analytical copy.
  5. What alternative would you choose? Compare relational vs document vs graph vs columnar against the dominant relationship/traversal pattern and query shape, not personal preference.

15. What to remember

The Core Mental Model

Data Representations is best understood as choosing, explicitly, which access pattern gets to be cheap — row-oriented for point access, columnar for scans — and binding that choice to a schema contract that survives independent evolution by producers and consumers.

The Production Insight

At scale, the main mechanism is only one component of the system. Schema-registry-enforced compatibility and workload-matched physical layout determine whether the format choice survives real, multi-team production traffic rather than a single-writer prototype.

The Staff+/Research Insight

The deeper principle is that a data format is a distributed-systems contract, not a file extension: every format decision is really a decision about which future schema changes are safe and which query shapes are cheap, made once and paid for by every future consumer.

Research, evidence, and what it means in practice

This pass replaces generic literature guidance with topic-specific research anchors. Each source is separated into what it demonstrated and how the idea is commonly operationalized today.

1. Designing Data-Intensive Applications, Chapters 2–4
Martin Kleppmann · 2017

What it demonstratedSystematically compared relational, document, and graph data models against the relationships and query patterns they make cheap or expensive, and formalized how binary encodings (Thrift, Protobuf, Avro) support schema evolution via field tags/numbers versus the fragility of positional encodings like CSV.

How practitioners use itTreat "which data model" as a question about the dominant relationship-traversal pattern in the workload, and require every shared binary schema to declare its forward/backward compatibility rule before it ships.

2. Column-Stores vs. Row-Stores: How Different Are They Really?
Abadi, Madden, Hachem · SIGMOD 2008

What it demonstratedShowed that the analytical performance advantage of column stores comes from a bundle of techniques (column-wise compression, late materialization, block iteration) rather than storage layout alone, and that naively "simulating" a column store on a row store recovers only part of the benefit.

How practitioners use itChoose Parquet/ORC specifically for the compression and predicate-pushdown machinery, not merely because "column-oriented" sounds modern; verify the query engine actually exploits column pruning.

Engineering ruleMeasure the first saturated resource under the production workload, then optimize that resource. Do not import an optimization solely because it improves a different benchmark regime.

Production Case Study — Migrating an events pipeline from JSON to Avro with a schema registry

System: Kafka + Confluent Schema Registry (Avro)Evidence: public documentation / documented industry patternScope: streaming ingestion + downstream analytics

Binding constraint

A growing set of independently-deployed producers and consumers shared raw JSON event payloads with no enforced schema, and an uncoordinated field rename silently broke a downstream aggregation job that had assumed the old field name.

Design intervention

Adopt Avro for the event payload, register the schema in a central registry with a BACKWARD compatibility rule, and reject any producer write that would violate compatibility before it reaches the topic.

uncoordinated schema drift → silent downstream breakage → registry-enforced Avro schema at write time → compatibility violations caught before ingestion

1. AI Engineer test

Can an engineer implement Data Representations without guessing hidden state, data contracts, or runtime behavior? The implementation lens is: identify the data model, physical layout, and schema evolution rule; then make input/output ownership, metrics, and failure handling explicit.

  • State the minimum observable inputs and outputs.
  • Name the dominant runtime resource rather than stopping at Big-O.
  • Define one invariant and one measurable regression signal.

2. AI Researcher test

Separate mechanism from evidence. For every important claim, ask whether it is a proven result, an empirical finding, or an engineering heuristic. The critical test for this topic is whether a claimed format advantage was measured on a workload with the same column-selectivity and update-frequency profile as production.

  • What baseline makes the comparison meaningful?
  • Which assumption would invalidate the result?
  • Does the conclusion survive a change in scale, data distribution, or evaluation metric?

3. Staff AI Engineer test

Can the technique survive production load and organizational complexity? Focus on schema ownership across independently-deployed teams. A design is incomplete until ownership, degradation behavior, rollback, and observability are specified.

  • Where is the stateful failure boundary?
  • What degrades first at p99 or under overload?
  • What can be changed independently without invalidating cached or persisted state?

4. First-principles teaching test

Reduce the chapter to a cause-and-effect chain: required capability → binding constraint → changed computation → new resource cost → new failure mode. If a paragraph cannot fit somewhere on this chain, it is probably context rather than mechanism.

  • Can you explain when the technique stops helping?
  • Can you derive the production bottleneck from the representation and execution path?
