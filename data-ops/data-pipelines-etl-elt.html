Data Pipelines: ETL & ELT

A production-and-research treatment organized for engineers who already understand ML, neural networks, and Transformer fundamentals. Each chapter is deliberately split into two reading pages: mechanism first, then systems, failure modes, and research reasoning.

In plain English

A data pipeline moves data from where it is produced to where it is used, and the modern data stack's big shift was moving the "transform" step from before loading (ETL) to after loading (ELT), so cheap cloud warehouses do the heavy lifting instead of a fragile, hand-maintained transformation server.

PAGE 1 · MECHANISM, MENTAL MODEL, THEORY

1. Quick explanation

The engineered flow that extracts data from source systems, moves it to a destination, and transforms it into a usable shape — either transforming before loading (Extract-Transform-Load) or after loading directly into a scalable warehouse/lakehouse (Extract-Load-Transform) — operating in batch, micro-batch, or streaming modes.

2. What problem does this solve?

Problem. Source systems (OLTP databases, SaaS APIs, event streams) store data in a shape optimized for their own operational needs, not for the joins, aggregations, and history that downstream analytics and ML need — so data must move and change shape, and it must do so on a schedule or continuously, without corrupting the source or falling behind.

Problem → constraint → design: Source-optimized data shape ≠ consumption-optimized data shape → limited transformation compute near the source, and consumers with different freshness needs → extract once, load into a scalable destination, then transform (ELT) or transform in flight before loading (ETL), choosing batch/micro-batch/streaming based on freshness requirements.

Why engineers care: removing the "transform before load" bottleneck by pushing transformation into the destination warehouse transfers pressure to warehouse compute cost and transformation-code governance — ELT makes it cheap to load everything raw, which then requires disciplined, version-controlled, testable transformation logic (the domain of tools like dbt) or the warehouse fills up with untested, ungoverned SQL.

3. How to think about it

Source systems (OLTP DB, SaaS API, event stream)
        │
        ▼
Extract (full/incremental) → Load raw into destination (ELT) OR Transform then Load (ETL)
        │
        ├── freshness mode: batch / micro-batch / streaming
        ├── transformation layer (SQL models, dbt, Spark jobs)
        └── quality/test gates on transformed output
        ▼
Analytics tables, feature stores, ML training sets, dashboards

A useful way to think about it: ETL is like a translator standing at the border, converting every document before it's allowed in; ELT is like letting every document in first (cheap, fast, complete) and hiring translators inside who transform documents on demand, in whichever order downstream consumers actually need.

Where this analogy stops helping: ELT's "translate on demand" step is not free — every transformation still consumes real compute in the warehouse, and letting untransformed raw data accumulate without governance produces exactly the ungoverned pile that centralized ETL was originally designed to avoid.

4. What is happening under the hood

  1. Represent the state. Source data is extracted either as a full snapshot or incrementally (change-data-capture logs, updated_at watermarks, or webhook/event streams), using connectors — Fivetran and Airbyte are the two dominant managed/open-source connector platforms for this step.
  2. Execute the topic-specific transformation. In ETL, transformation (cleaning, joining, aggregating, deduplicating) happens in a separate compute layer before the data lands in its final destination. In ELT, raw or lightly-cleaned data is loaded directly into a cloud warehouse or lakehouse first, and transformation happens afterward using the warehouse's own compute — commonly orchestrated as layered SQL models with a tool like dbt (staging → intermediate → mart layers).
  3. Apply constraints and allocate resources. The freshness mode is chosen per use case: batch (nightly full loads, cheapest, highest latency), micro-batch (every few minutes, the modern-data-stack default via scheduled dbt runs and incremental Fivetran/Airbyte syncs), or streaming (sub-second, via Kafka/Kinesis/Flink, reserved for use cases that cannot tolerate batch latency, such as fraud detection or real-time feature serving).
  4. Preserve the right state. Idempotent, incremental loading (merge/upsert semantics keyed on a stable identifier, watermark-based extraction) preserves correctness under retries and partial failures; transformation layers are version-controlled and tested (dbt tests, CI) so that a bad transformation can be rolled back like application code.
  5. Validate the failure boundary. The primary failure pressure is a transformation bug or a schema change at the source silently propagating incorrect data into every downstream table that depends on it, since ELT's "load everything raw, transform later" pattern means many derived tables can share one upstream failure.
ETL: transform-then-load, bounded destination compute, opinionated schema at load time. ELT: load-then-transform, elastic destination compute, raw data preserved as a re-processable source of truth.

The resource that usually becomes the problem: warehouse compute cost from re-running transformations over growing raw data volumes, and the blast radius of an untested transformation change propagating through a dependency graph of derived tables.

6. How it scales

At a high level, as the workload grows: the number of source connectors, the volume of raw data landed, and the depth of the transformation DAG all grow, and each stresses a different part of the pipeline. The practical bottleneck is warehouse compute cost and transformation blast radius, which may dominate before extraction throughput does.

T_request = T_queue + T_compute + T_memory + T_network + T_validation

The practical question is: at what raw data volume, transformation DAG depth, and refresh frequency does re-running transformations over accumulated raw data become the first saturated resource (warehouse compute cost), and at what freshness requirement does batch stop being viable and streaming become necessary? Those thresholds are more actionable than a blanket "batch vs streaming" preference.

A practical production starting point: for most analytics workloads, use a managed connector platform (Fivetran or Airbyte) for extract-and-load, land data raw into a cloud warehouse or lakehouse, and use dbt for the transformation layer with version-controlled models, tests, and documentation; reserve a dedicated streaming path (Kafka + Flink or a cloud-native equivalent) only for the subset of use cases with a genuine sub-minute freshness requirement.

  • Keep durable state behind explicit ownership boundaries.
  • Make workers independently replaceable.
  • Version caches and artifacts.
  • Isolate slow or failure-prone dependencies behind queues, deadlines, and budgets.

Use the simpler approach when: data volume is small and a nightly batch answers the business question. Use the more production-ready approach when: multiple teams need to reprocess or re-derive tables differently from the same raw source, which favors ELT's "load raw once" pattern. Choose streaming when: a measured business decision genuinely requires sub-minute freshness. Avoid both naive batch-only design and premature streaming when: you haven't measured the actual freshness requirement against the added operational cost.

10. Common misunderstandings

Misconception: "ELT is strictly better than ETL because it's the modern approach."
Reality: ELT trades transformation compute cost and governance discipline for load simplicity and reprocessability; when destination compute is expensive or governance is weak, ETL's bounded, curated loading can be the more predictable choice.
Why people believe it: the "modern data stack" narrative (Fivetran/Airbyte/dbt/cloud warehouses) is heavily marketed as a replacement for legacy ETL, obscuring that it's a trade-off, not a strict improvement.

Misconception: "Streaming pipelines are always more valuable than batch because they're real-time."
Reality: most analytics and even many ML training use cases tolerate minutes of staleness, and streaming infrastructure adds meaningfully more operational complexity (stateful processing, exactly-once semantics, backfill difficulty) that is only worth it when a real decision needs sub-minute data.
Why people believe it: "real-time" sounds unambiguously better, and the cost of unnecessary streaming infrastructure is invisible until an incident requires reprocessing history.

Misconception: "Once data is loaded (ELT), the transformation layer is just SQL and doesn't need the same engineering rigor as application code."
Reality: transformation models form a dependency graph that many downstream consumers rely on, so they need version control, tests, code review, and CI just like any other production code — this is exactly what dbt was built to enforce.
Why people believe it: SQL feels like a query, not a program, so it's easy to skip the software-engineering discipline that a compiled pipeline job would obviously require.

11. The point where this starts to hurt

The system appears scalable because loading raw data is cheap and fast, but the real bottleneck is warehouse compute cost from re-running transformations over growing raw data, and the blast radius of an ungoverned transformation change. Capacity planning must therefore model transformation DAG depth and incremental-processing coverage — not only raw data ingestion volume.

12. How to explain it in an interview (30–45 seconds)

"A data pipeline moves and reshapes data from source systems to where it's consumed, either transforming before loading (ETL) or loading raw and transforming afterward in the destination (ELT), in batch, micro-batch, or streaming mode depending on freshness needs. It exists because source systems store data in a shape optimized for their own operations, not for downstream analytics or ML. Operationally, the modern default is extract-and-load via a managed connector like Fivetran or Airbyte, land data raw in a warehouse or lakehouse, and transform it with a version-controlled, tested SQL layer like dbt. I think of ELT as trading transform-before-load discipline for load-then-transform flexibility, which only pays off if the transformation layer gets the same engineering rigor — tests, ownership, incremental processing — as application code. The main trade-off is reprocessability and simplicity of loading versus warehouse compute cost and governance burden. In production I would measure warehouse compute cost per transformation run and the blast radius of the dependency DAG, because ELT's convenience at load time can hide an expensive or fragile transformation layer."

13. Follow-up questions you may get

  1. What is the dominant resource at scale? Short answer: measure warehouse compute cost per transformation run and whether models use incremental versus full-refresh materialization.
  2. What assumption makes the mechanism work? Idempotent, incremental extraction (stable keys, watermarks, merge/upsert semantics) assumes retries and partial failures are safe to replay without duplicating or corrupting data.
  3. Where does it fail first? An untested transformation model or an unannounced source schema change propagates incorrect data through every downstream table in the DAG before anyone notices.
  4. What is the simplest production baseline? Managed extract-and-load (Fivetran/Airbyte) into a warehouse, with dbt-modeled, tested, version-controlled transformations, defaulting to micro-batch freshness.
  5. What alternative would you choose? Compare ETL, ELT, and streaming against the source system's transformation compute headroom, the destination's elasticity, and the actual measured freshness requirement.

15. What to remember

The Core Mental Model

Data Pipelines: ETL & ELT is best understood as a decision about where transformation compute lives — before loading, near the source, or after loading, inside an elastic destination — and that decision determines whether governance discipline must live in a separate transform service or inside a version-controlled SQL modeling layer.

The Production Insight

At scale, the main mechanism is only one component of the system. Incremental, idempotent loading and a tested, owned transformation DAG determine whether a pipeline survives retries, schema drift, and growing data volume rather than silently corrupting downstream tables.

The Staff+/Research Insight

The deeper principle is that ELT did not eliminate the need for engineering discipline in transformation logic — it relocated that discipline from a dedicated ETL service to a SQL modeling layer, and organizations that treat SQL models as informal queries rather than production code simply rediscover the same governance failures in a new location.
